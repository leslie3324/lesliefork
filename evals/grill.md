# `grill` 评估问题

在干净的 Agent 上下文中执行。检查是否先读项目上下文、分轮追问、把事实与待决定项分开，并在实现前让用户确认可观察的验收标准。Agent 应建议规模/并行/文档方式，但由用户决定。

## 应触发

1. “想给现有订单服务加取消退款，但规则还没完全定。先帮我把需求问清楚，不要设计和写代码。”
2. “这个功能验收只写了‘用户能正常使用’，请找出需要向产品确认的业务结果、边界和异常场景。”
3. “我给了 PRD、会议纪要和现有代码；找出冲突，先从代码能确认的地方查起，再问我会影响范围或验收的问题。”

## 不应触发或边界案例

1. “把这个变量名从 `foo` 改成 `bar`，直接修改代码。”
2. “解释一下什么是幂等”，没有提出项目需求或实现任务。

## 期望行为

- 不提前拍板技术方案；只追问会影响目标、范围、业务规则、验收或风险的问题。
- 验收标准写成可观察、能判定通过/失败的结果；关键标准未确认时不交给 `plan`。
- 汇总 Agent 建议的轻量/结构化模式、文档和并行机会，并明确让用户选择。
- 用户未选择正式文档前不创建文档；用户选择后使用现有模板，将确认内容写入 `overview.md`。
- 用户文档简洁、重点前置；长篇分析不混入正式文档。
