# `plan-large-feature` 评估问题

每个案例都应在干净的 Agent 上下文中执行。重点检查回答是否区分事实和决策、是否拆分模块和任务、是否标记优先级和依赖，以及是否把模块关系放在最后一个主要章节。

## 应触发的案例

1. “为一个已有 Java 服务增加 OAuth 登录和 MCP 会话续期，涉及网关、用户绑定、Token 存储、Session 管理和审计，请先做中大型功能计划，不要写代码。”
2. “把现有单体里的研究 Skill 发布流程拆成 Git、打包、测试环境、生产发布和回滚模块，列出主次任务和模块关系。”
3. “这个跨三个服务的批量导入功能应该怎么拆？需要明确数据流、失败恢复、幂等和验证方式。”
4. “为已有服务规划一项 MCP 连接器接入：父目录有 AGENTS.md，`docs/` 可能被忽略，旧环境还需要一次性补偿 SQL。先给计划，不要创建文件。”

## 不应触发或边界案例

1. “把这个变量名从 `foo` 改成 `bar`，直接修改代码。”
2. “已经批准的计划只有一个测试文件要补充，给我执行步骤。”

## 期望行为

- 规划阶段不修改生产代码。
- 有代码仓库时检查需求中明确提到的事实，并标记未知项。
- 先识别适用的父级 `AGENTS.md` 及其引用规范；对拟写入路径区分已跟踪、未跟踪和被忽略状态。
- 明确文档、发布 SQL 与一次性补偿 SQL 的交付边界；未确认时不创建、不暂存，也不把基线已有文档误判为分支改动。
- 使用 P0/P1/P2 标记优先级，明确任务依赖。
- 为每个模块描述职责、接口、所有权和验证方式。
- 最后给出模块关系总结，再给出待确认决策和下一步行动。
