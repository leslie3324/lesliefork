# `plan` 评估问题

每个案例都应在干净的 Agent 上下文中执行。重点检查 Plan 是否只消费已对齐需求、先列简明用户摘要、在编码前锁定可观察的验收标准、把验收映射到测试/E2E，并尽量识别真实可并行任务。

## 应触发的案例

1. “为已有 Java 服务增加 OAuth 登录和 MCP 会话续期。先基于已确认的业务需求做实现计划，给出可观察的验收标准、至少一条端到端场景和任务依赖，不要写代码。”
2. “这项批量导入跨三个服务。尽量拆出可并行的垂直交付，每项关联验收 ID、接口契约、所有权和局部验证；指出串行依赖和集成负责人。”
3. “验收目前只写了‘导入成功’，但没说部分失败、重复提交和结果如何判定。不要自行补业务规则，返回 grill 列待确认项。”
4. “主 feat worktree 已有。按仓库治理计划一项 MCP 连接器改造；`docs/` 可能被忽略，发布还涉及一次性补偿 SQL。先检查路径状态和交付边界，不创建文件。”

## 不应触发或边界案例

1. “把这个变量名从 `foo` 改成 `bar`，直接修改代码。”
2. “已经确认的简单改动只补一个测试，直接实现；不要重复启动完整 Plan。”

## 期望行为

- 需求缺少改变方向或验收的业务决定时，Plan 停止并返回 `grill`。
- Plan 结束、实现开始前，每条验收标准已明确且由用户确认；任务与验收 ID 关联。
- 对用户可见或跨模块业务链路规划 E2E 入口、业务结果、环境/数据、断言和证据；不以 HTTP 200 单独判定成功。
- 优先最大化可行并行度，但共享契约或有依赖的任务必须标出前置关系；用户确认后才派发。
- 规划阶段不修改生产代码；读适用规则、当前实现和文件状态；不创建未确认文档或发布物。
- 给用户的首屏摘要简洁；Agent 执行说明不重复需求，整体 Review 与 E2E 在集成后执行。
