# 文档治理规范

> 本文档是 agent 协作的**公共文档治理规则**，所有项目通用。
> agent 在创建/维护项目文档前先读本文件，了解：什么时候建、建什么文档、怎么命名、信息以谁为准。

## 适用场景

本结构用于用户确认采用结构化文档的需求：主 feat worktree 建好后，先做需求澄清；用户确认需要文档后，才在 `docs/<分支名>/` 下初始化 MVP 文档。是否属于小改动、是否并行和是否建文档由用户决定；Agent 负责给出依据充分的建议，不擅自替用户定级。已有内容不覆盖。
日常小改动、临时排查、一次性脚本默认不建这套文档。

## 核心原则

1. **职责前置**：每份文档最前面写清当前文档职责，让新会话一眼知道该读什么。
2. **只记已确认**：正式文档只写已确认内容。待定项必须显式标注「待确认」——零散事项放进 overview 的「待确认问题」或 decisions 的「待处理」段；大段未定稿的草稿、推演放 `_scratch/`，确认后才进正式文档。
3. **及时回写**：用户确认过的结论要同步进文档，不要只留在聊天上下文里。
4. **单一权威源**：同一信息只在一处是权威，其他地方只能引用不能复制，避免并行修改时双写冲突。
5. **按需生长**：先建 MVP 文档，需要时再拆分新类型，不要一次铺满。
6. **面向读者**：正式文档给用户和团队成员阅读，先呈现结论、目标、边界、验收标准和待决策项；保持简洁，不放 Agent 的长篇推理或重复的任务提示。
7. **Agent 执行说明分离**：派发任务时需要的文件范围、接口约束、验证命令等从正式文档和代码事实中提炼。默认作为执行上下文传递，不另存重复需求；确需跨会话保存的未定分析放入 `_scratch/`，并明确它不是权威结论。

## 目录约定

- 中大型需求在项目根 `docs/` 下按分支名建目录，例如 `docs/feat/ywy/ai_usage_board/`。
- 文档跟代码同仓、走同样的 review（docs-as-code）。

## 初始化模板

文档的初始结构和内容只维护在 [templates/](templates/)；创建脚本读取模板，其他规则和 Skill 不重复定义目录树。

模板的状态头使用 `{{date}}` 占位符，创建时替换为当天日期。模板目录中的 `.gitkeep` 只用于 Git 保留空目录，不写入需求文档。

- `overview.md` 是需求权威源，承载简明摘要、已确认结论、可观察的验收标准与「待确认问题」（待确认问题直接放文末）。
- `design.md` 早期把接口作为其中一节；接口稳定、前端要对接时再拆出 `api-contract.md`。
- `decisions.md` 与 `_scratch/` 分工：前者记零散的待确认/已决事项（文字条目），后者放大段草稿和推演过程。
- `module-breakdown.md` 是并行执行地图：用精简任务表展示交付结果、验收项、依赖、边界和验证；详细 Agent 指令按需单独派发，不把用户文档写成长篇操作提示。

## 验收与端到端测试

- 开始实现前，需求和技术计划必须明确可观察、可判定的验收标准；标准未确认或关键结果不可验证时，先回到需求澄清，不开始实现。
- 对用户可见或跨模块的业务流程，计划阶段先定义至少一条端到端（E2E）验收路径：从真实用户/外部入口执行到业务结果，并说明测试环境、数据前置条件、断言和证据来源。代码集成后运行 E2E；E2E 不等于只测浏览器，也不等于只检查 HTTP 成功。
- E2E 不适用或环境暂不可用时，计划必须写明具体原因、替代验证和残余风险，并由用户确认；不得静默省略或把未执行写成通过。

## 渐进扩展（需要时才创建）

| 触发条件 | 新增文档 | 职责 |
|---|---|---|
| 接口要给前端对接 | `api-contract.md` | 前端对接接口文档：路径、方法、入参、响应结构、字段说明 |
| 用户确认并行开发 / 派给多个 agent | `module-breakdown.md` | 可供用户审阅、Agent 执行的精简任务与依赖地图 |
| 进入联调测试 | `interface-test-report.md` | 接口级测试报告：启动方式、请求参数、HTTP 状态、原始返回 |
| 准备测试或生产发版 | `release-checklist.md` | 分环境记录部署步骤、待办及实际发版结果 |

新建文档后，在 `index.md` 用一张表标注「已建 / 待建」，让新会话一眼知道当前处于哪个阶段。

## 发版纪要规则

- 测试和生产共用一份 `release-checklist.md`，不另建 `release-record.md`；分环境保留部署步骤、待办和执行结果，不能互相覆盖。
- 每个环境按“开发分支、网关配置、定时任务、SQL、Apollo 配置、高频接口、数据中心协助、其他、发布结果”记录，并注明执行顺序。
- 确认不适用的项目写“无”；未确认写“待确认”、未执行写“待执行”，不得把计划写成实际结果。
- 接口详情、联调过程和测试明细引用对应文档，不在发版纪要重复展开。

## 备注

- 项目内**不再单独放治理文档**，规则以本公共文件为唯一权威；项目特例写进该项目的 `index.md`。
