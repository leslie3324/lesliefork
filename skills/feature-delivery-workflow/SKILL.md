# 功能交付流程编排

只负责判断阶段、传递交接信息和控制确认闸门，不替代各专业 Skill 的具体规则。

## 模式

- `smart`：根据需求规模和改动类型选择阶段。
- `full`：依次执行规划、编码、日志审查、提交前验证和适用的交付阶段。
- `plan-only`：只规划，不修改生产代码。
- `implement`：实现功能并同步使用日志指导；普通迭代不自动执行耗时验证。
- `pre-commit`：只执行提交前验证闸门，不自动创建提交。
- `delivery`：处理提交前验证、接口文档和 MR 前置工作，但不自动推送或创建 MR。

默认使用 `smart`；用户未明确要求完整流程时，不强制调用本 Skill。

## 阶段

1. 中大型、跨模块或跨服务需求：使用 `$plan-large-feature`。规划未确认前不进入生产代码实现。
2. 编写后端代码：同步使用 `$coding-logging-guidance`，实现后再次审查日志覆盖和用户上下文。
3. 普通实现迭代：不因单次修改自动触发编译、测试、打包、启动服务、启动容器或全量 lint/type-check；默认只做必要的轻量检查，例如 `git diff --check`。
4. 提交前验证：当用户要求提交、执行 `git commit`、准备提交、交付本次改动、准备 MR，或明确要求验证时，进入提交前验证闸门。先检查工作区和差异，再根据改动范围选择最小有效验证：受影响模块编译、相关测试、格式/静态检查、配置加载校验或接口/数据库契约验证。验证失败时不得提交，除非用户明确确认带着失败结果提交。
5. 全量验证：仅在用户明确要求、发布/MR 前、高风险跨模块或跨服务改动，或最小验证不足以覆盖改动时执行全量测试、完整打包、启动服务或容器。
6. 检测到接口变化：询问用户是否使用 `$api-integration-docs`，并让用户选择 `yapi`、`postman` 或 `feishu`。
7. 用户明确要求准备 MR：使用 `$git-workflow` 的 MR 流程；只要求准备时不创建远程 MR，创建分支、提交、推送和 MR 按确认范围执行。准备 MR 前必须完成适用的提交前验证，并确认 source、target、工作区提交状态和验证结果。

## 提交前验证闸门

进入该阶段后，按以下顺序执行：

1. **确认范围**：查看 `git status --short`、`git diff --stat`、`git diff --check`，确认没有把无关改动纳入验证或提交。
2. **选择最小验证**：
   - 文档、注释、Markdown：差异检查，必要时 Markdown 检查。
   - 配置文件：格式校验或最小加载校验。
   - Java 普通业务代码：受影响模块编译和相关测试。
   - Java DAO、Entity、公共接口：受影响模块编译、相关测试；必要时扩大到依赖模块。
   - TS：受影响包的类型检查和相关测试。
   - Go：受影响 package 的测试，必要时编译。
   - Rust：受影响 crate 的检查/测试，必要时构建。
   - API、数据库、权限、跨服务协议：相关测试和契约验证，不能只做静态检查。
3. **执行并记录**：报告实际执行的命令、结果、耗时（若可得）和未执行的验证。
4. **作出闸门结论**：全部适用验证通过后，才允许继续执行用户明确要求的 `git commit`；任一关键验证失败则暂停，不自动提交。

验证命令应优先使用当前仓库已有的构建脚本、测试脚本和项目规则，不要在通用 Skill 中硬编码某个目标仓库或绝对路径。

## 交接信息

每个阶段结束时输出并传递：`workflow_id`、范围、阶段状态、改动文件、接口是否变化、日志事件、验证结果、未决决策和下一步。长流程可将其保存到临时的 `.codex/workflows/<workflow_id>/state.md`，小流程直接在对话中交接。

## 确认闸门

- 规划完成后，未获用户确认不得开始生产代码修改。
- 普通实现迭代不因“实现完成”自动进入耗时验证；提交、交付、MR 或用户显式验证请求才触发提交前验证。
- 接口文档只在用户选择目标后生成；远程推送、飞书写入和请求执行保持各自 Skill 的确认规则。
- MR 创建前必须确认 source、target、工作区提交状态和验证结果。
- 任何阶段发现范围扩大、接口契约不确定或验证失败时，暂停并报告阻塞项。

单测属于版本化交付，必须随业务代码提交。为降低多人并行开发的冲突，新需求优先新增功能专属测试类，避免持续向通用测试类堆叠；只有依赖个人环境的 `*LocalTest`、`*ManualTest` 等临时测试可以不纳入 Git。

日志不是编码完成后的替代品，而是编码期间同步加入、完成后再审查的横切阶段。
