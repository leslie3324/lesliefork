# 准备提交

1. 先核对仓库、当前 worktree 和分支：业务需求只在主 feat 分支提交。若当前是目标分支的冲突候选，只允许提交仍未合并 MR 的目标适配或冲突解决；后续功能、业务修复和其他需求改动停止提交并回到 feat，不把候选分支当成后续工作的默认位置。
2. 检查本次差异、暂存范围和未完成操作，不纳入无关改动；验证实际待提交内容，未暂存差异不能让验证对象与提交对象错位。
3. 获取最新 pro，分析提交关系、冲突及相关业务影响；给出是否同步及方式，确认后才更新 feat。
4. 核对 [review-diff](../review-diff/SKILL.md) 报告是否覆盖本次完整需求及实际待提交内容，基线、内容标识和相关上下文是否有效；缺失则安排独立需求级审查，变化则补受影响复审，不逐任务或重复完整审查。有本次未解决问题、影响交付的未决项或审查阻塞就停止；存量归属、闭环与轮次按该 Skill，不自动扩大修复范围。
5. 按仓库规则，只执行本次需求相关模块的最小必要编译、相关测试和检查，不扩展到无关模块或全量验证；只改文档不跑业务构建。失败或结论未明就停止提交。验证期间若修改了待提交内容，先补受影响 Review 和验证，不能复用修改前结论。
6. 返回能否提交及验证证据：仓库、已验证内容的 Git tree/文件摘要、基线 SHA、覆盖范围、命令、运行条件和结果，以及有效 Review 报告/未决项；计划在部署后执行的 E2E 明确写待验收，不能用 Review 或编译冒充。只要求检查不提交，明确要求提交且检查通过才按确认范围提交，项目人工审批另按规则执行。

## Maven 私有依赖缓存异常

当 Maven 编译报告私有依赖中的类或方法找不到时，先核对依赖的 GAV、有效依赖来源，以及本机缓存 JAR 的内容；不要仅凭 `cannot find symbol` 就认定业务源码有错。若源码确实依赖该符号，而本机同 GAV JAR 不含该符号，并有依据表明私有仓库中同版本制品已被重发（例如上游未递增版本号），按以下步骤处理：

1. 将 groupId 转为路径，精确定位本机 Maven 缓存中的 `<groupId路径>/<artifactId>/<version>`；确认目标在 Maven 本地仓库，不在项目工作区，也不是整个 `.m2`、group 或 artifact 目录。
2. 如果当前任务包含修复构建阻塞或提交前验证，确认 GAV 和精确路径后可直接清理该版本缓存目录，再从项目配置的私有仓库重新执行原构建/测试命令；如果用户只要求诊断，或目标路径无法唯一确认，先说明准确路径并询问。不要清理整个 Maven 仓库或无关版本。
3. 下载后检查 JAR 时间/内容及目标类，再重跑原失败命令。若私有仓库下载的同版本 JAR 仍缺少目标符号，停止重复清缓存，报告仓库制品未更新，并请制品维护者发布可用制品或递增版本。

不要在输出中暴露私有仓库凭据、settings 中的认证信息或含秘密的完整下载日志。`-U` 可用于强制检查 SNAPSHOT 更新；对本地已有的同版本 release JAR，若私有仓库重发了相同版本，先清理上述精确本地缓存再解析。

后续发布复用这份证据：相同内容、基线、范围和运行条件且验证成功，不重跑。仅暂存或提交相同内容不使验证失效；代码、依赖、配置、测试数据、环境或基线变化时，重做受影响检查。缺少可核对证据不能跳过，当前差异/暂存范围仍须检查。
