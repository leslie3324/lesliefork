# 候选资格与决策

逐项判断，不给加权总分：一个硬约束失败不能被高 stars 或其他优点抵消。任务范围明确后再评估；候选以实际适配能力为单位，不能把整个仓库的声誉当作某个子 Skill 的效果证据。

## 合格门槛

| 门槛 | 要核验的事实 |
| --- | --- |
| 功能适配 | 直接覆盖核心成功条件；读到对应实现/规格，不能仅凭关键词、同名或未来 roadmap |
| 运行适配 | 语言、运行时、Agent、部署、数据方向、传输、认证与现有约束兼容；不能以大改架构掩盖不适配 |
| 主源证据 | 检查实际源码、`SKILL.md`、包内容、schema/规格或可复现运行路径；只读 README/demo/营销页不足 |
| 维护状态 | 核对是否归档、提交/发布、兼容与相关问题响应；长期稳定项目可用稳定性证据，不以更新时间一刀切 |
| 许可与风险 | 确认适用 License/服务条款、依赖、数据流和所需权限；已知高风险未解决或许可不兼容不得推荐；风险未知不称安全 |
| 成本与可逆性 | 说明安装/部署范围、集成工作、运行成本、退出方式和锁定风险；证据不足用范围/未知，不捏造工时 |

记录资格：`qualified`（本次门槛均有支持）、`partial`（仅适配一部分）、`unverified`（关键事实未知）、`rejected`（明确失败）。后三类不进入合格推荐表，但可作为局部参考、待验证项或排除项，写明缺口。

`qualified` 不等于实测通过。阅读指令不能证明 Skill 效果，schema 存在不能证明连接可用，官方宣称支持不能证明当前环境已跑通。运行验证状态另列；关键不确定性可能改变采用决定时建议 PoC，不直接给已验证的 `adopt`。

## availability：是否有符合本次要求的方案

- `suitable_candidate_found`：至少一个完整路径通过门槛；若是组合路径，还须核验组件及组合接口，不能仅凭“理论上能拼”。
- `partial_candidates_only`：没有完整合格方案，只有局部匹配或关键能力待核验的相关方案；明确说明没有符合全部要求的可复用方案。
- `no_suitable_candidate`：本次检索未发现可用完整方案，也没有值得继续验证的相关候选。说明范围与覆盖缺口；来源失败本身不能证明此结论。

搜索严重受限时仍报告当前候选状态，但结论限定为已获取证据，推荐 `defer`，不由低覆盖直接推导必须自研。

## decision：下一步建议，不是执行许可

| 值 | 使用条件 |
| --- | --- |
| `adopt` | 已有合格完整方案，集成代价合理；注明尚未执行的环境验证 |
| `extend` | 已核验可复用底座，明确小范围扩展能填补缺口；列扩展项、上游变更风险和许可，不把只借鉴原则称作扩展依赖 |
| `compose` | 已核验多个组件与组合路径能满足要求；列接口和维护代价，关键可行性未明则先 `poc` |
| `poc` | 有值得验证的方向，但关键兼容、能力或效果未确认；定义最小步骤、通过标准和停止条件 |
| `build` | 没有合格方案，或已有方案的适配/集成代价明显不合理；指出自研缺口和可借鉴部分，不自动进入编码 |
| `defer` | 关键需求、证据、访问能力或预算不足以决策；列明恢复条件 |

`adopt` 必须对应 `suitable_candidate_found`。`extend` 或 `compose` 若仍缺完整已核验路径，保持 `partial_candidates_only`，不要伪装成现成可用；`build` 可以在有候选但成本不合适时使用，不等同于“世上不存在”。

采用、扩展、组合和 PoC 都写清否决/停止条件，如核心场景失败、超出权限或成本边界、必须泄露登录凭据；失败后回到决策，不降低验收标准迁就候选。
