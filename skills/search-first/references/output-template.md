# 输出契约

先给一句结论；小任务可用简短条目，大调研再展开表格。字段含义固定，不要求机械输出大篇模板；没有数据的字段写未知/未执行，不补造。默认在对话交付，不因模板要求写文件。

## 结论与范围

- `as_of`：查询/核验日期。
- `need`：能力缺口与成功条件；`environment`：目标环境；`constraints`：硬约束和非目标。
- `availability`：`suitable_candidate_found / partial_candidates_only / no_suitable_candidate`。
- `decision`：`adopt / extend / compose / poc / build / defer`，理由及关键取舍。
- `coverage`：实际查询词、已检索来源；不可用/跳过的来源、原因和对结论的影响。

## 候选及证据

合格候选最多 3–5 个；没有就写 0 个。局部/待核验/排除项另列，不冒充推荐。

| 候选/资格 | 适配能力与缺口 | 主源 URL、版本/tag/commit、查询日期 | 证据状态与运行结果 | 维护/License/权限与数据风险 | 集成、运行成本和退出风险 |
| --- | --- | --- | --- | --- | --- |

证据状态使用 `inspected / observed / snippet_only`；引用精确文件或官方章节。发布日与查询日分开，未运行就写“未运行”。对排除项给具体失败条件，不用“star 少”“不够成熟”代替理由；不需要罗列所有搜索噪声。

## 下一步与 plan 交接

- `unknowns`：会改变结论的未知项，已有事实不能重新标为待用户决定。
- `validation`：本次已运行检查及结果、未运行检查；不得把候选自带测试或别人的 benchmark 写成本次验证。
- `next_step`：推荐路径、待用户确认事项和停止条件。需要 PoC 时列最小步骤、目标环境/数据、可判定成功标准和所需权限；授权前不执行。
- `plan_handoff`：引用确认需求及验收；给方案/版本、可复用部分、自研缺口、集成边界和验证风险。建议 `build` 不代表用户已确认编码；`defer` 不自动推进。

无方案可用措辞：

> 截至 YYYY-MM-DD，在已检索来源中未发现符合要求的可复用方案。相关项目仅覆盖 A，未满足 B；建议自研 C / 验证 D / 等待 E。未覆盖来源为 F，本结论不代表世界上不存在。
