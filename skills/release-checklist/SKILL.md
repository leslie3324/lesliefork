# 发版纪要

只维护需求目录中的 `release-checklist.md`。它是生产发版待办与执行结果的记录，不是设计文档、接口文档或测试报告。

## 范围与取证

1. 先从目标项目向上读取适用的 `AGENTS.md` 和其引用的文档治理规则；默认目标是 `docs/<功能分支>/release-checklist.md`。
2. 确认本次功能范围、发布分支或提交范围、生产目标和当前状态。用户明确要求“生成”或“更新”时，可写入该文档；只要求讨论、审查或预览时只在回复中给出草案。
3. 仅从本功能分支、明确的 SQL/配置文件、需求目录和用户已确认的测试结论取证。不要将相邻需求、历史遗留项或泛化运维检查混入。
4. 只记录已确认的执行事项。信息不足但会阻塞发布时，写成明确的“待确认”待办并说明需要谁确认；不得猜测生产配置、SQL 或发布版本。
5. 不记录密钥、Token、密码和私钥值。记录配置键、密文/受控配置的位置和配置责任人即可。

## 编写规则

- 使用项目治理规定的分段顺序：开发分支、网关配置、定时任务、SQL、Apollo 配置、高频接口、数据中心协助、其他、发布结果。
- 每条只写“对象 + 要执行的动作 + 执行前提/顺序”。不适用时写“无”。
- 可以使用代码块粘贴执行所必需的准确 YAML、Properties、SQL 或命令；配置内容完整是必要条件时可以完整粘贴。代码块只保留实际要执行的内容，不在其中或其后解释实现逻辑。
- SQL 按 DDL、DML、发布后 SQL 的实际执行顺序列出，写清文件路径或 SQL 块；没有 SQL 时写“无”。
- 网关配置只写需要新增或变更的路由、鉴权类型、配置位置及执行动作。仅在上线实际需要时记录接口路径或路由 SQL，不展开接口定义。
- Apollo 配置只写 key、namespace/环境、值或取值来源、是否需要重启/灰度及配置顺序；敏感值写“由受控密文配置提供”。
- 发布前将“发布结果”标为“待执行”，并保留生产目标、计划发布版本和已完成的测试环境验证结论的链接。发布后只回写实际版本、时间、结果和回滚状态。

## 禁止混入

- 实现流程、架构说明、业务规则、代码逻辑、日志方案和代码验收清单。
- 非网关执行所必需的接口路径清单、入参/出参、字段说明或接口测试明细。
- 配置原理、设计取舍、风险推演、故障排查过程和长篇安全说明。
- 测试步骤、测试数据、断言与详细结果；只引用测试报告或记录“测试环境已验证”。
