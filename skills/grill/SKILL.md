# 需求澄清

在主 feat worktree 中工作。先读适用的 `AGENTS.md`、现有需求文档和相关代码；区分已确认事实、假设、冲突和待用户决定项。能从仓库查明的问题先查，不要求用户重复提供。

## 澄清要求

- 分轮提出少量关键问题，只问会改变目标、范围、业务规则、验收结果或风险的问题；不提前设计技术实现。
- 与用户确认目标、范围/非目标、约束、关键业务规则和可观察的验收标准。按 Given/When/Then 或等价形式写清前置条件、触发行为和预期结果；错误、权限、状态、幂等等只在相关时纳入。
- 找不到明确的业务验收结果或仍有会改变实现方向的未决项时，停在需求澄清，不进入实现；列出具体待确认项。
- 向用户建议轻量或结构化推进方式、可能并行的任务、是否需要文档及其成本；规模、文档和并行模式由用户决定。并行优先寻找，但不在用户确认任务拆分前派发 Agent。

## 文档与交接

- 用户选择结构化文档后，使用文档治理模板；在已有 worktree 中执行 `skills/start-feature/scripts/start_feature.py <repo> <branch> <worktree> --init-docs`。只有用户确认并行开发时才加 `--parallel`。
- `overview.md` 是需求和验收标准的唯一权威来源。仅写已确认结论和明确标注的待确认问题；保持用户可读、重点前置。
- 不把长篇 Agent 推理或任务提示写进正式文档。必要的未定分析放 `_scratch/`；派发 Agent 时从正式文档提炼任务边界，不复制需求。
- 交给 `plan` 的输入必须包括已确认的验收标准和未决项；Plan 不得替用户补定业务预期。
- 需求明确且存在可复用能力缺口或用户要求找现成方案时，先调用 [search-first](../search-first/SKILL.md)，将报告与需求一起交给 `plan`；小 bug、已定选型、普通 API 用法或用户明确跳过时不强制调研。不在 `grill` 复制检索与评估规则。
