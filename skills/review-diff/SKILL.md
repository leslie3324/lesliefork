# 需求差异审查

按需求维度审查：开发与集成完成后审一次完整需求，不为每个任务、文件或小修改单独安排 Review。多个仓库分别记录基线与内容，并核对跨仓库契约。只有修复或待审内容变化才复审，不做风险分级，也不默认多 Reviewer 投票。

## 审查输入与工作区

1. 读取目标仓库及路径内适用的 `AGENTS.md`、相关 `REVIEW.md`、已确认需求与验收标准；有 `overview.md` / `design.md` 就引用，不另写需求副本。以需求为准核对实现，不把作者解释当成正确性证据；发现方向冲突或关键业务决定缺失，交回用户，不按实现反改预期。
2. 固定本次需求的审查基线，核对当前 HEAD、索引、工作区及本次新增文件；不假定 `HEAD` 或某个分支名就是基线。阅读、记录 [输出与证据契约](references/report-and-evidence.md)，确保审查覆盖实际待交付内容，不只覆盖已提交 diff。
3. 由独立于作者的 Reviewer 上下文审查，在调用方已授权的独立 worktree 中工作；已有合适 worktree 就复用。主 Agent 将精确待审版本及本次未提交、新增内容准备到那里，不修改原工作区或索引，不自动提交、推送或合并。未准备完整快照或缺少独立审查能力，标明阻塞/未执行，不以作者自审冒充独立 Review。
4. 审查前后记录 Reviewer worktree 的 HEAD、`git status`、内容摘要和 Git mode/文件类型；Reviewer 默认不修改业务代码、暂存、提交、推送，不操作主工作区。报告放业务树外或已确认的证据位置。独立 worktree 只隔离工作区，不保证强制只读；意外写入、模式/类型或 HEAD 变化就停止、报告差异，不自动清理或合回。

## 怎么审

- 以完整需求 diff 为入口，按问题追查相关实现、调用方、接口/数据契约、配置和测试；不是只看改动行，也不扫描所有无关模块。重点判断是否解决需求、符合系统约束、引入回归；修 bug 时核对根因和修复是否覆盖同类触发路径。
- Finding 必须说明可触发条件、实际错误与证据，给真实文件和行号；不凭文件名猜问题，不把缺少上下文当成确定 bug。严重程度用于排列 findings，不用于建立需求风险等级或放宽授权。
- 默认过滤纯格式/lint、无行为影响的命名偏好、清理建议及重复 findings；这些不触发作者修改或新增审查轮次。真实行为、安全、契约问题不能因看似小而过滤。
- 默认读取已有测试/命令结果，必要的编译、测试仍由 `prepare-commit` 按项目规则执行；仅有明确授权或必要验证时做最小复现，不自动构建、启动服务或执行 E2E。审查、编译测试、业务验收分别给结论，未运行不写通过。

## 问题来源

来源与严重程度分开记录，用固定的需求基线比较问题行为，不以“这一行没改”或 `git blame` 单独定性：

| 来源 | 判定与处理 |
|---|---|
| `Introduced` | 本次引入，纳入本次修复闭环；后续轮次才发现也不变成存量问题 |
| `Aggravated / Activated` | 缺陷原本存在，但本次扩大影响或新增触发路径；纳入本次闭环 |
| `Pre-existing` | 基线已有同样问题，本次没有增加其影响；相关问题单列，不算本次引入，不默认要求顺手修或据此阻止本次交付 |
| `Uncertain` | 来源无法证明，列基线/行为证据缺口，不猜测归属；影响交付决定时交用户确认 |

其他任务、作者或仓库引入的问题不自动算存量；看它是否属于本次需求。严重存量问题明确提醒用户另行处理，不自动扩大修复范围。无关存量问题不继续展开。

## Finding 闭环与收敛

- 首轮看完整需求，报告沿用稳定 Finding ID。主 Agent 在已批准实现范围内把问题交实现者处理；Reviewer 不替作者修。每条可交付 finding 最终是修复并复核，或说明误报/有意行为/无需处理理由后关闭；需要新的业务决定或扩大范围则保持待用户处理。
- 修复由 Reviewer 核对当前代码和必要证据后关闭，作者说“已修复”不等于关闭。已有结论不重复报告；同类问题一次列全本次相关实例，不通过逐行新增 finding 制造回合。
- 复审重点是相对上次被审内容的新增 diff、未解决问题和必要上下文；需求基线不随轮次重置。发现新改动改变原判断时可扩展相关范围，说明原因；无变化不重审、不默认跑满轮次。
- 同一需求自动审查/修改最多三轮；第三轮仍不收敛、双方结论冲突或用户要求介入时停止自动循环，报告未决问题与重新评估方案的原因。不得换 Reviewer、工作区或基线偷偷重置轮数；用户另行决定下一步。
- 交付前核对报告的基线、内容标识（含 mode/类型）和上下文仍有效；仅暂存/提交相同内容与文件模式可复用 AI Review。内容、文件模式/类型、基线或相关契约变化就补受影响复审，冲突解决也一样；无可靠内容证据不得沿用旧 `pass`。AI 结论不代替项目人工审批，新 commit 的人工批准按项目规则重新核对。

## 输出与改进

按 [输出与证据契约](references/report-and-evidence.md) 返回本次问题、相关存量问题、处理状态、内容标识、审查轮次和未验证事项，明确“未发现本次问题”不等于“没有残余风险”。将报告保存在调用方已确认位置；未指定时放系统临时目录并返回路径，不自动创建正式文档、远程评论或评审服务。

记录实际处理结果与轮数，不只统计 bug 数，也不把未裁决项算成误报。真实漏报、误报、事故及重复报告可经确认沉淀到项目测试或 Skill `evals/`；反复出现的规范问题建议前移到 lint、项目规则或简短 `REVIEW.md`。不自动修改其他项目规则、配置或长期记忆，不引入每日评测/指标平台。
