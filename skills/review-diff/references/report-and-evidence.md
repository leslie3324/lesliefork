# 输出与证据契约

## 被审内容

- 标识需求、仓库、源工作区、Reviewer worktree、固定需求基线 SHA、源 HEAD、审查轮次和时间。多个仓库逐个记录，不用一个 SHA 代表整条跨服务需求。
- 对已提交且干净的版本记录被审 commit SHA 和 tree SHA；有未提交内容时，HEAD tree 不代表实际被审内容，必须补本次文件清单、存在/删除及重命名状态、Git mode/文件类型和字节摘要，包含新增文件及必要的二进制文件。符号链接记录链接目标字符串本身，不跟随目标读取内容；相同字节但可执行位或文件类型不同不算相同快照。只计算本次范围，但把影响判断的外部契约/依赖列作上下文。
- 未提交快照由调用方准备，不在用户索引执行 `git add` 来凑 tree。复制文件或应用 patch 后核对源与 Reviewer 的路径、存在状态、mode/类型、链接目标及字节摘要一致；普通 `git diff` 不包含 untracked，不能据此认为覆盖完整。排除无关改动和秘密，不复制整个工作区或凭据。
- 记录 Reviewer 开始快照以及结束时的 HEAD、status、内容摘要和 mode/类型；因为准备未提交快照，Reviewer status 本来就可能是脏的，要求前后相同而不是结束时必须 clean。报告文件放业务树外，构建产物也不应混进待审内容。
- 仅暂存/提交相同文件内容及 mode/类型，AI Review 可复用；新 SHA 不自动等于新内容。内容、文件模式或类型变化不能沿用旧 pass，先用新增 diff 补审；基线或契约变化须重新核对来源和影响。报告缺文件、无摘要/模式证据或上下文不可核对时，不能以“分支名相同”复用。

## 最小报告

先给本次问题数量、相关存量问题数量和结论。无本次问题时明确写“未发现本次引入或放大的问题”，同时说明审查范围、未执行验证和未决项。作者回复记录为事实，不作为独立审查依据。

```text
需求 / 仓库：
需求基线 SHA / 源 HEAD：
被审 commit / tree SHA（适用时）：
本次文件清单、状态、mode/类型、链接目标与内容摘要（未提交时必需）：
本次变化模型 / 受影响的旧假设：
反例审查覆盖（已核对边界及未覆盖项）：
运行版本与依赖契约核对：
Reviewer worktree / 前后状态核对：
轮次 / 时间：
结论：pass / needs_changes / needs_user / blocked
本次问题数 / 相关存量问题数：

本次问题：
相关存量问题（Pre-existing）：
来源不确定项（Uncertain）：
未执行验证 / 残余风险：
报告路径：
```

每条 finding 至少保留：

| 字段 | 内容 |
|---|---|
| ID | 首次分配后沿用；文件/行号变化不自动新建问题 |
| 严重程度 | 如 P1/P2/P3，说明实际后果；不是需求风险分级 |
| 来源 | Introduced / Aggravated / Activated / Pre-existing / Uncertain |
| 位置 | 当前被审版本中的真实文件:行号；跨仓库带仓库标识 |
| 问题与证据 | 触发条件、错误行为、调用链/代码/已有测试证据、相关基线证据 |
| 修复方向 | 最小修正方向，不为了关闭问题擅自扩大需求 |
| 状态与理由 | open / fixed / resolved / needs_user，保留复核结果或关闭理由 |

`fixed` 只在 Reviewer 核对修复后使用；`resolved` 要保留理由，涉及业务取舍需用户决定。Pre-existing 可记录“另行处理，非本次范围”，不强制修复。严重存量问题仍显著提醒，不能因分类隐藏。

## 结论与复审

- `pass`：实际范围已审，当前内容证据有效，已完成正向审查和由变更模型驱动的第二遍反例审查，本次 findings 已修复并复核或有依据地关闭，没有影响交付的未决项。需要说明反例审查覆盖的边界、未覆盖项，并核对受影响的旧调用方和实际运行版本/依赖契约；只有测试通过、只审正常路径或缺少兼容性证据时不能判 `pass`。允许同时列未运行测试与残余风险；pass 是代码审查结论，不是构建/E2E/生产批准。
- `needs_changes`：有未解决的本次问题，交作者在已批准范围内修复。
- `needs_user`：取舍、来源不确定或三轮仍未收敛，需用户决定；不能以新的审查请求自动清空未决问题。
- `blocked`：缺基线、准确快照、必要上下文或独立审查能力，或 Reviewer 意外修改代码/HEAD；说明无法完成的范围，不报告 pass。

复审更新同一报告或引用前版，不丢失 finding ID、关闭理由和轮数。再次发现已关闭问题时先检查是否由新改动重新引入；没有新证据不重新打开。下一轮仍未解决的旧 ID 不重复计为新增 bug。

轻量记录人/作者对 findings 的实际处置：修复、误报、有意行为、无需处理、未裁决，以及审查轮数。无人工裁决时不声称误报率已确认；规则/工具/模型变化时用已有真实案例验证漏报、噪音和收敛，不要求每次构建完整指标体系。
