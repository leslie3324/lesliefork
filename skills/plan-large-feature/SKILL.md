# 中大型功能规划

这是规划阶段 Skill。未获得执行确认前，不修改生产代码、不创建实现脚手架、不声称方案已批准。

## 仓库与交付物前置检查

在读取业务代码、创建文档、生成 SQL 或暂存文件前，完成以下检查并把结果记为事实：

1. 从目标仓库或 worktree 向上找到适用的 `AGENTS.md`；若其引用文档或发布治理规范，先读取对应规范。
2. 对每个拟创建或修改的文档、SQL、配置和发布物，先用 `git ls-files` 与 `git check-ignore -v --no-index -- <path>` 区分已跟踪、未跟踪和被忽略状态。
3. 明确每个交付物的目的地：版本化源码、项目文档、发布平台、一次性运维脚本，或仅在回复中交付。未获明确授权时，不要因为“上线可能会用到”就把一次性 SQL、补偿 SQL 或临时文档加入仓库。
4. 对目标分支已存在的文档，用 `git diff <base>...HEAD -- <path>` 确认它是否是本分支改动；不要把继承自基线的已跟踪文件误判为本分支引入，也不要为清理而删除它。
5. 规划阶段结束前，列出拟版本化的文件和拟在仓库外执行的动作；交付边界不明确时，作为待确认项，不创建或暂存文件。

## 规划要求

- 先检查仓库和现有调用链，区分**事实、决策、假设、阻塞项**；未知内容不要猜。
- 当前事实必须包含：适用治理规则、相关路径的 Git 跟踪状态，以及文档和 SQL 的交付边界。
- 先写用户可感知的结果、范围、约束和非目标。
- 按可验证的垂直切片拆分少量内聚模块，不要只按前端/后端罗列工作。
- 每个模块说明：职责边界、接口、数据所有权、输入/输出、副作用和验证方式。
- 任务使用 `P0`（关键路径）、`P1`（必要配套）、`P2`（加固或后续），并写清任务 ID、范围、前置依赖、验收条件和验证方式。
- 按需补充兼容性、迁移、权限、可观测性、发布、回滚和失败恢复；不相关内容不要展开。

## 输出顺序

1. 目标、范围、非目标和成功标准。
2. 当前事实、决策、假设和阻塞项。
3. 模块设计。
4. 按关键路径排序的任务表。
5. 风险、验证和发布事项。
6. **模块关系**：最后一个主要章节描述入口到结果的数据流、调用依赖、边界、失败处理、可并行部分和关键路径。

结尾必须列出待用户确认的决策、推荐下一步，并说明规划阶段没有修改生产代码，也没有创建或暂存未经确认的文档、SQL 或发布文件。
