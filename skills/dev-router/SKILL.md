# 开发阶段路由

本 Skill 只负责路由，不替代阶段 Skill，也不实现 Agent 的主循环。主循环由 Agent 自身的目标、工具调用和结果反馈完成；这里只决定“现在在哪、下一步是什么、何时必须停”。

## 模式

- `auto`（未指定模式时的默认值）：识别当前阶段和下一步，只给建议，不加载或执行其他阶段 Skill。
- `stage:<阶段>`：只进入用户指定的一个阶段，不推断后续流程；读取该阶段对应的 `SKILL.md` 后按其规则执行。
- `end-to-end`：仅在用户明确要求完整流程时使用；只读取当前阶段对应的 `SKILL.md`，遇到任何确认闸门立即停止，不预读后续阶段。

不要因为用户说“继续”就当作已授权执行全部阶段。继续只表示可以重新判断当前事实和下一小步。

## 先判断是否适用

以下任务不启用完整开发流程，直接建议对应的单个 Skill 或普通处理：

- typo、纯文档小修、单文件低风险改动：直接完成，不创建需求文档或 worktree。
- 只调查、只查日志：使用 `troubleshoot`，不把调查包装成开发阶段。
- 只审一份已经完成的差异：使用 `review-diff`，不自动向前补 `start-feature`/`grill`/`plan`。
- 只执行一个明确动作，例如 Apollo、MySQL、Maven 或发版材料：直接路由对应 Skill。

只有需求会改变代码或配置行为、需要多步实现，且用户明确要求按流程推进时，才使用下面的完整阶段图。

## 完整阶段图

按事实选择最早的未满足阶段，不按用户声称的进度直接跳过：

| 阶段 | 进入条件 | 当前阶段必须做 | 进入下一步所需证据 |
|---|---|---|---|
| `start-feature` | 要做代码改动，尚未确认仓库/分支/worktree | 确认完整分支名，从最新 `origin/pro` 创建主 feat worktree | 分支、基线 SHA、worktree 已确认 |
| `grill` | 目标、范围、规则或验收结果仍有歧义 | 查仓库事实，只问会改变结果的问题 | 验收标准已由用户确认 |
| `search-first` | 存在需选型的可复用能力缺口 | 调研并给出采用/验证/自研决定 | 选型和适用边界有证据 |
| `plan` | 需求和验收已确认，准备决定实现方式 | 收口方案、测试、E2E 和并行边界 | 用户确认方案与验收计划 |
| `implement` | 方案已确认并获准修改 | 由主 Agent 按确认范围实现和集成 | 完整需求差异已形成 |
| `review-diff` | 本次需求已集成，准备提交前审查 | 独立审查完整差异和必要上下文 | 无未解决的本需求 finding |
| `e2e-verify` | Review 已收敛，准备业务验收 | 从真实入口验证已确认的验收标准 | 本地可执行时，完整本地 E2E 已有证据 |
| `prepare-commit` | Review 和本地 E2E 已完成 | 核对待提交内容并做最小有效编译/测试 | 用户明确授权提交，或明确得到“不能提交”结论 |
| `prepare-release` | 提交已完成，目标是测试/生产发布 | 准备 MR、部署步骤和发版事实 | MR/材料已准备；远端写入和部署另行授权 |

`release-checklist`、`apollo-config`、`mysql-change`、`maven-publish` 是发布过程中的条件分支，只在本次确实涉及该动作时读取，不默认加入每个需求。

## 门禁与懒加载

- 不读取未来阶段的 `SKILL.md`。只读取当前阶段的 Skill；下一步只给名称、原因和进入条件，不把内容提前塞入上下文。
- `auto` 只路由，不读取任何阶段 Skill。`stage` 和 `end-to-end` 确认当前阶段后，只主动读取一个 `../<阶段>/SKILL.md`；当前 Skill 自己明确引用的必要文件可以读取，但不预读未来阶段。`implement` 和 `bypass` 没有独立阶段 Skill。
- Review、编译测试和 E2E 是不同证据，不能互相代替。Review 没发现问题不等于 E2E 通过。
- 本地能启动、连接或 mock 本次涉及的真实依赖时，完整 E2E 必须在提交前执行；部署后 E2E 是追加验证。
- 文件写入、代码修改、外部写入、提交、推送、MR、部署和不可逆操作都需要各自授权；`end-to-end` 不包含这些授权。
- 缺少分支、验收标准、Review 证据或 E2E 证据时返回阻塞，不以“应该没问题”补齐。
- 用户改变需求或出现新事实时重新路由；不要为了流程完整而强行继续原阶段。

## 输出格式

`auto` 和 `stage` 默认只返回：

```text
模式：
当前阶段：<阶段名或 bypass>
判断依据：
下一步：
能否提交：能 | 不能 | 不适用
需要确认：
不会执行：
```

`end-to-end` 额外给出“已完成的当前步骤”和“停止原因”；等待用户确认后，再从最新事实重新路由。不要预演尚未获授权的后续动作。

当前阶段早于 `prepare-commit`，或缺少 Review / 本地 E2E 证据时，`能否提交` 必须明确写 `不能`。只做单个阶段或命中 `bypass` 时优先写 `不适用`；保守写 `不能` 也有效。只有 `prepare-commit` 已核对实际证据后才能写 `能`。
