# 实现规划

这是技术规划阶段，不是需求访谈或编码阶段。输入应来自 `grill` 已确认的需求和验收标准；可以是对话，也可以是用户选择创建的正式文档。

## 开始前

- 读取目标仓库及路径层级内适用的 `AGENTS.md` 和它引用的规范；先看当前分支、差异和相关实现。
- 区分事实、决策、假设和阻塞项。若业务目标、范围或验收结果仍有歧义，返回 `grill` 澄清，不代替用户决定。
- 规划期间不修改生产代码。创建正式文档、SQL、配置或发布材料前，确认用户已选择相应产物及其位置；检查目标路径的 Git 跟踪/忽略状态，不覆盖已有内容。

## 规划要求

- 先给最小可行方案和必要取舍；只展开会影响实现、验收、成本或风险的内容。
- 默认主动寻找最大可行并行度。按可独立验收的结果拆任务，明确模块/文件所有权、接口契约、依赖、局部验证和集成负责人；有真实依赖或共享改动冲突的任务才串行。
- 给出任务依赖图或等价的并行分组，说明哪些可以同时开始、哪些被什么阻塞。只有用户确认并行拆分后才创建 `module-breakdown.md` 或派发 Agent。
- 每项任务都关联验收标准 ID，写清交付结果和可执行的局部验证。Agent 使用独立 worktree；主 feat worktree 是集成根，主 Agent 负责集成、整体 Review 和端到端验收。
- 按需说明兼容性、权限、并发、幂等、数据迁移、观测、发布和回滚；不相关项不展开。

## 验收与端到端测试门禁

- **Plan 结束、编码开始前，验收标准必须明确并由用户确认。** 每条标准都必须描述可观察的预期结果，且能判定通过或失败；不确定的业务预期返回 `grill`，不能由 Plan 推测补齐。
- 将每条验收标准映射到验证方式：单元、集成、契约或 E2E。对用户可见或跨模块业务流程，至少规划一条从真实业务入口到最终业务结果的 E2E 场景；明确环境、数据前置条件、操作、断言和证据来源。E2E 不限定浏览器，也不能只凭 HTTP 成功判定业务正确。
- E2E 在代码集成后执行，但场景与成功标准必须在实现前约定。环境或能力暂不可用时，列出替代验证、残余风险和需要用户接受的缺口；不静默省略、不声称未运行的测试通过。
- 若判断 E2E 不适用，说明具体原因，并选择能覆盖变更风险的替代验证。

## 文档与结束条件

- 正式文档给用户和团队阅读：先写结论、目标、边界、验收和待决策项；保持简洁。`overview.md` 是需求及验收标准的权威来源，`design.md` 记录方案；并行任务只在用户确认后写入 `module-breakdown.md`。
- Agent 执行说明只补充负责边界、接口、文件范围和验证命令，引用正式文档，不复制需求；默认随任务派发，不额外生成长篇内部文档。
- 先展示精简的用户决策摘要，再给必要的技术细节、任务依赖和验证矩阵。列明待确认项、文档/并行建议及下一步。
- **只有当用户确认实现方案、任务拆分、验收标准和 E2E 计划后，Plan 才算完成并可进入编码。**
