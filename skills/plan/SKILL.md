# 实现规划

这是技术规划阶段，不是需求访谈或编码阶段。输入应来自 `grill` 已确认的需求和验收标准；可以是对话，也可以是用户选择创建的正式文档。

## 开始前

- 读取目标仓库及路径层级内适用的 `AGENTS.md` 和它引用的规范；先看当前分支、差异和相关实现。
- 先读权威需求材料（PRD、协作台账、配置表、接口文档），再核对代码与 `specs/` 的现状——功能可能已经实现或部分实现，不要从 Story 标题或聊天转述推断范围。材料里的“待确认”原样带入规划，不自行补全。
- 区分事实、决策、假设和阻塞项。若业务目标、范围或验收结果仍有歧义，返回 `grill` 澄清，不代替用户决定。
- 存在需选型的可复用能力缺口却没有调研结论时，先调用 [search-first](../search-first/SKILL.md)；已定选型、简单改动或用户明确跳过时不强制。消费报告的 `availability`、`decision`、证据与未知项，不重做完整调研；没有合格候选不能包装为 `adopt`，`poc` 要计划验证门槛，`defer` 要列恢复条件。仅在约束或关键事实变化时定向补查。
- 规划期间不修改生产代码。创建正式文档、SQL、配置或发布材料前，确认用户已选择相应产物及其位置；检查目标路径的 Git 跟踪/忽略状态，不覆盖已有内容。

## 规划要求

- 先给最小可行方案和必要取舍；只展开会影响实现、验收、成本或风险的内容。
- 默认主动寻找最大可行并行度。按可独立验收的结果拆任务，明确模块/文件所有权、接口契约、依赖、局部验证和集成负责人；有真实依赖或共享改动冲突的任务才串行。
- 给出任务依赖图或等价的并行分组，说明哪些可以同时开始、哪些被什么阻塞。只有用户确认并行拆分后才创建 `module-breakdown.md` 或派发 Agent。
- 每项任务都关联验收标准 ID，写清交付结果和可执行的局部验证。Agent 使用独立 worktree；主 feat worktree 是集成根，主 Agent 负责集成及安排独立 Review、端到端验收，不用作者自审代替独立审查。
- 按需说明兼容性、权限、并发、幂等、数据迁移、观测、发布和回滚；不相关项不展开。

## 多需求并行与 Agent 编队

- **按能力/仓库切任务，不按 Story 切。** 同一仓库或模块只设一个写 Agent；多个 Story 落在同一 repo 时，由一个 Agent 串行完成或按文件所有权硬切，否则 entity/mapper/migration 的冲突成本会吃掉并行收益。
- **先立共享底座。** 多个 Story 依赖同一份元数据、价格口径、分组模型或权限模型时，先把底座做成可独立验收的交付（表结构 + 接口契约 + 迁移号段），再派发消费它的 Story；底座在关键路径上，应最先开工。
- **资料完整度决定能否开工。** 只给资料完整的 Story 派实现 Agent；低完整度的只派澄清/核对，待“待确认”转成结论后再排期。不要把“有 Story”等同于“可开发”。
- **澄清拓扑 ≠ 实现拓扑。** 需求澄清可以一个 Story 一个会话；实现必须收敛到仓库/能力，不能让 N 个 Story 对应 N 个写 Agent。
- **编队起步 3+1**：3 个开发 Agent（按仓库/能力）+ 1 个独立验收 Agent；每多一个真正独立的仓库或能力再加 1 个。验收 Agent 在独立 worktree 中分阶段执行 `review-diff` 与 `e2e-verify`，分别输出代码审查和业务验收结论，不因职责拆分再固定增加 Agent；worktree 隔离不等于强制只读。
- **跨 Agent 的契约先冻结**：接口字段、入口默认值矩阵（哪个入口默认开/关）、单一价格口径、迁移号段、文件所有权，写进共享文档后再并行。回答“要几个 Agent”时同时说明为什么不是 N+1、为什么不是 N-1。

## 需求级代码审查

- 开发与集成完成后、交付提交前，由主 Agent 安排独立上下文、独立 worktree 的 [review-diff](../review-diff/SKILL.md) 审一次完整需求；不为每个任务安排局部 Review，不做风险分级。多仓库需求涵盖各仓库本次差异及跨仓库契约。
- 计划给出需求基线、完整待审内容的准备方式、Reviewer、报告位置，以及与编译测试、E2E 的分工。审查包含本次未提交和新增文件，不只检出旧 HEAD；准备或创建 Reviewer worktree 沿用已有授权，不修改主工作区。
- Finding 归属、噪音过滤、内容绑定和最多三轮的修复/复审只按 `review-diff` 维护。主 Agent 在已批准范围内交作者修复，未收敛或需业务取舍时回到用户；不为了前置审查增加每次修改后的构建/测试。
- 代码审查与业务验收分别按 `review-diff`、`e2e-verify` 输出结论，可由同一独立验收 Agent 分阶段执行，不因职责拆分固定增加 Agent；独立 worktree 不等于强制只读。

## 验收与端到端测试门禁

- **Plan 结束、编码开始前，验收标准必须明确并由用户确认。** 每条标准都必须描述可观察的预期结果，且能判定通过或失败；不确定的业务预期返回 `grill`，不能由 Plan 推测补齐。
- 将每条验收标准映射到验证方式：单元、集成、契约或 E2E。对用户可见或跨模块业务流程，至少规划一条从真实业务入口到最终业务结果的 E2E 场景；明确环境、数据前置条件、操作、断言和证据来源。E2E 不限定浏览器，也不能只凭 HTTP 成功判定业务正确。
- E2E 在代码集成后、计划约定的环境执行：本地可验收时在交付前，依赖测试部署时在部署后；场景与成功标准在实现前约定。环境或能力暂不可用时，列出替代验证、残余风险和需要用户接受的缺口；不静默省略、不声称未运行的测试通过。
- 若判断 E2E 不适用，说明具体原因，并选择能覆盖变更风险的替代验证。

## 文档与结束条件

- 正式文档给用户和团队阅读：先写结论、目标、边界、验收和待决策项；保持简洁。`overview.md` 是需求及验收标准的权威来源，`design.md` 记录方案；并行任务只在用户确认后写入 `module-breakdown.md`。
- Agent 执行说明只补充负责边界、接口、文件范围和验证命令，引用正式文档，不复制需求；默认随任务派发，不额外生成长篇内部文档。
- 先展示精简的用户决策摘要，再给必要的技术细节、任务依赖和验证矩阵。列明待确认项、文档/并行建议及下一步。
- **只有当用户确认实现方案、任务拆分、验收标准和 E2E 计划后，Plan 才算完成并可进入编码。**
