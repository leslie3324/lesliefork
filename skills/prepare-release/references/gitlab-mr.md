# MR 规则

## 内容语言

- MR 标题、描述及其他供人阅读的内容使用中文，包括变更内容、关联需求、验证情况、风险与影响、回滚方式和备注/待确认事项。
- 若仓库要求 `feat/fix` 等类型前缀，只保留前缀，标题正文写简短的中文变更摘要，例如 `feat(连接器): 支持多凭证重授权`；不直接照抄英文 commit subject、分支名或文件路径。
- 分支名、SHA、文件路径、命令、接口/字段名、错误码和第三方产品名等标识保留原文；需要解释时，在标识后用中文说明。
- 未执行的验证写“未执行”或“待验收”，没有相关项写“无”，暂时无法确认写“待确认”；不得把计划写成已执行。

## 描述结构

MR 描述至少包含以下段落；简单变更可以合并段落，但不能省略验证、风险和回滚信息。

```markdown
### 变更内容
说明要解决的问题和本次实际改动。

### 关联需求
需求、Issue 或文档链接；没有时写“无”。

### 验证情况
列出实际执行的命令、测试或环境验收及结果；未执行或待验收的项明确标注。

### 风险与影响
说明兼容性、配置、数据、调用方和发布范围等影响；没有已知影响时写“无已知影响”。

### 回滚方式
说明回滚提交、关闭 Feature Flag 或其他恢复步骤。

### 备注
记录 Review 证据、待确认事项或需要 Reviewer 重点关注的内容；没有时写“无”。
```

- 确认源、目标、项目和已有 MR；本地/远程源不一致先说明，不偷偷换源或推送。
- 所有 MR 都查原 feat 的 test 回灌历史：看合并父、引入差异及相关 MR/历史来源，不只看分支名或最新 test HEAD；共有正式基线或 feat 自己的提交不算污染。已污染或来源不明就停止发布。
- 获取最新源/目标并固定 SHA，在独立 worktree 真实预演 `目标 <- feat`，用未合并索引判断冲突，不把目标合回原 feat；命令失败不能报无冲突。只清理自己的未编辑预演，不强删 worktree。
- 无冲突用原 feat；有冲突才建立候选分支。先读取目标仓库的分支命名和 CI `branch_check` 规则，再从固定目标 SHA 在独立的一次性 worktree 中创建唯一候选分支（例如 `git worktree add <candidate-worktree> -b <valid-candidate-branch> <target-sha>`），不得假定 `codex/...` 是合法前缀。主 feat worktree 不得切到候选分支；候选分支不得跨 MR 复用。
- 只在候选 worktree 中把 feat 单向合入候选，默认使用 `git merge --no-commit --no-ff <feat-ref>`；不得用 rebase 或批量 cherry-pick 替代 merge 来组装候选。先理解双方意图，取舍确认后解决，意图未明不自行选边。候选只承载目标适配和冲突解决，不承载后续功能、业务修复或其他需求改动；这些改动必须先落在 feat。test 候选只能提回原 test，不能回 feat 或提到 pro。
- 候选 MR 未合并期间若 feat 又有新提交，先完成并验证 feat，再把最新 feat 合入同一候选，补受影响 Review 与验证；这是仅为更新 MR 源分支的单向同步，不代表后续开发改在候选进行。候选 MR 一旦合并、关闭或废弃，停止更新该候选；后续工作回到 feat，需要新 MR 时从当时最新目标重新创建候选。
- 冲突解决后检查未合并索引和完整差异，在提交合并结果之前按 prepare-commit 核对准确候选快照，补受影响 Review 与必要验证；未通过或仍有未决项不得提交。验证与授权满足后使用 Git 准备的默认 merge message（`git commit` 不带 `-m`），不要复制源 feat 的提交标题，避免候选历史里出现与 feat 原提交同名的伪重复提交。核对候选提交以目标分支为第一父、feat 来源为第二父；若目标仓库只能 squash 或线性合并，目标历史不会保留该双亲关系，须在 MR 记录 feat SHA、候选提交或 tree SHA 及冲突解决结果，不得声称已保留完整提交关系。
- 候选 MR 设置合并后删除源分支，只对一次性候选启用，绝不对原 feat 启用。合并后核对 MR 已合并、目标包含预期内容、远程候选已删除；随后在主 feat worktree 核对仍在 feat，并按删除授权清理本地候选 worktree 和分支。删除失败、受保护或存在其他引用时如实报告，不宣称已清理。MR 关闭而非合并时，不自动删除，先确认候选是否仍需保留。
- 推送候选分支、创建候选分支 -> 原目标分支的 MR 分别按明确授权执行，并检查 CI branch check 与冲突状态。
- 合并后的内容、基线、相关契约或运行条件影响原结论时，须在提交/发布前补受影响 Review 与验证；不能用原 feat 的审查/验证冒充候选已验证。发布前重新核对 SHA 和被审内容证据，变化就重新分析，项目人工批准绑定当前 commit。
- 验证通过且提交/推送/创建 MR 在确认范围内才发布；只要求准备时不创建远程 MR。读回方向和状态，返回链接，不自动修改/关闭旧 MR 或合并，不丢弃未提交解决成果。
