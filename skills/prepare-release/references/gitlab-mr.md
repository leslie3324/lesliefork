# MR 规则

- 确认源、目标、项目和已有 MR；本地/远程源不一致先说明，不偷偷换源或推送。
- 所有 MR 都查原 feat 的 test 回灌历史：看合并父、引入差异及相关 MR/历史来源，不只看分支名或最新 test HEAD；共有正式基线或 feat 自己的提交不算污染。已污染或来源不明就停止发布。
- 获取最新源/目标并固定 SHA，在独立 worktree 真实预演 `目标 <- feat`，用未合并索引判断冲突，不把目标合回原 feat；命令失败不能报无冲突。只清理自己的未编辑预演，不强删 worktree。
- 无冲突用原 feat；有冲突才建立候选分支：先读取目标仓库的分支命名和 CI `branch_check` 规则，再从最新固定的目标 SHA 建候选分支（例如 `git switch -c <valid-candidate-branch> origin/test`），不得假定 `codex/...` 是合法前缀。把 feat 合入候选分支（例如 `git merge --no-commit --no-ff <feat-ref>`），先理解双方意图，取舍确认后解决；意图未明不自行选边。test 候选只能提回原 test，不能回 feat 或提到 pro。
- 冲突解决后检查未合并索引和完整差异，在提交合并结果之前按 prepare-commit 核对准确候选快照，补受影响 Review 与必要验证；未通过或仍有未决项不得提交。验证与授权满足后，若用 `git merge --no-commit`，提交时不要用源 feat 的提交标题作为 `-m`；使用 Git 准备的默认 merge message（`git commit` 不带 `-m`），避免候选历史里出现与 feat 原提交同名的伪重复提交。核对候选提交有目标分支作为第一父提交、feat 来源作为第二父提交；推送候选分支、创建候选分支 -> 原目标分支的 MR 分别按明确授权执行，并检查 CI branch check 与冲突状态。
- 合并后的内容、基线、相关契约或运行条件影响原结论时，须在提交/发布前补受影响 Review 与验证；不能用原 feat 的审查/验证冒充候选已验证。发布前重新核对 SHA 和被审内容证据，变化就重新分析，项目人工批准绑定当前 commit。
- 验证通过且提交/推送/创建 MR 在确认范围内才发布；只要求准备时不创建远程 MR。读回方向和状态，返回链接，不自动修改/关闭旧 MR 或合并，不丢弃未提交解决成果。
